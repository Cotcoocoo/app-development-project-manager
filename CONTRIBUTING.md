# Contributing

Thanks for contributing to `app-development-project-manager`.

## Scope

Keep contributions focused on reusable application-development project management. Do not add rules tied to a private project, a personal file path, unreleased product details, credentials, customer data, or tool-specific assumptions unless they are explicitly documented as optional and broadly applicable.

## Before proposing a change

1. Search existing issues and pull requests for related discussion.
2. Explain the concrete user request or failure mode the change addresses.
3. Preserve the distinction between verified facts, assumptions, risks, and pending decisions.
4. Avoid turning the Skill into an implementation framework, a legal opinion, or a security certification.

## Editing guidelines

- Keep `SKILL.md` in imperative, operational language.
- Keep behavior platform-neutral unless a platform-specific section is clearly optional.
- Prefer concise checklists, decision rules, and evidence-based state definitions.
- Do not invent fixed timelines, performance thresholds, legal conclusions, or test results.
- Preserve privacy-first defaults and explicit confirmation for publication or external sharing.
- Update `README.md` and `CHANGELOG.md` when behavior or installation guidance changes.

## Pull requests

Use the pull request template. A contribution is ready for review when it:

- explains the problem and intended user impact;
- identifies changed files and any behavior changes;
- contains no secrets, private paths, personal data, or unrelated generated files;
- has been reviewed for clarity, consistency, and Markdown rendering;
- updates the changelog when the change affects users.

## Reporting issues

Use GitHub Issues for reproducible bugs and well-scoped feature requests. Do not disclose security vulnerabilities in public issues; follow [SECURITY.md](SECURITY.md).
